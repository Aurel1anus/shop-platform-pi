# 开发蓝图

本蓝图基于 2026-10-26 的代码状态，仅规划后续开发，不代表占位能力已经实现。

## 当前基线

- Go 电商后端已拆出，包含商品、购物车、订单、虚拟支付、优惠、评价和原始知识资料。
- pi 1.4.0 已接通 CLI、SDK、项目扩展与技能加载，已有 shop_status 状态工具。
- 已验证真实模型调用状态工具及三个只读商品工具（get_product、list_products、list_product_skus）；“列表→详情→规格”经 Python 客户端调用 Go 的真实模型链路已跑通。固定只读工具/服务场景已通过 npm run check:commerce:live 并记录首次基线（quality/README.md）；批量模型场景评分和开发者独立练习仍待补齐。记忆、RAG、HTTP/SSE 仍为空占位。
- 原始语料包含 294 个商品 JSON 和 827 条 FAQ；8 份评测集共 477 条，其中检索 300 条、记忆 10 条。
- 现有 Web 是管理/商家后台，消费端以原 Android 为主；新项目尚无网页聊天界面。

## 目标架构

```text
用户网页 / Android
         |
         v
Go API：统一鉴权与对外业务入口
         |
         +------ 商品 / 购物车 / 订单 ------> MySQL
         |                   |
         |                   +------------> MinIO（文件）
         |
         +------ /agent/* 转发 ------> Node Agent 内部服务
                                        |
                                        +-- HTTP/SSE、请求生命周期
                                        +-- pi SDK / SessionManager
                                        +-- .pi/extensions/
                                        |      +-- commerce：业务工具
                                        |      +-- harness：上下文、策略、事件
                                        +-- .pi/skills/：任务指引
                                        +-- src/retrieval/：自写 RAG
                                                   |
                                                   +-- 原始资料 / 检索索引
```

Go 业务数据只有 Go 写入；Agent 通过 HTTP 操作。Go 验证并转发用户凭证，Node 不信任客户端随意提交的 account_id。Node 内部服务无需直接对公网开放。

语言约定更新：新增具体业务接入、检索与数据处理优先使用 Python；pi SDK 会话和扩展注册继续使用 JS/TS，通过必要的薄适配连接 Python，不重复实现业务逻辑。当前只迁移商品详情 HTTP 客户端，不增加常驻 Python 服务；图中的 RAG 等后续业务实现遵循此约定，既有空占位不代表必须使用 TypeScript。

完整对话优先由 pi 原生 SessionManager 保存。harness 负责账号归属、会话并发、消息/run 映射、业务引用与事件，不重写模型循环和另一套完整对话格式。

## 第一阶段：只读商品工具

目标：在 CLI 中完成“查询商品—查看规格—说明结果”，作为第一个业务闭环。

主要位置：src/clients/commerce.py、.pi/extensions/commerce/catalog.ts 与 index.ts；扩展仅负责工具注册和调用 Python。

交付：

- Python Go API 客户端与 pi 薄适配，统一超时、错误转换和取消传递。同步 Python 请求采用 socket 等待超时；适配层负责整次调用时限、取消子进程及回收，不能把仅有 socket 超时视为取消链路已完成。
- list_products、get_product、list_product_skus；明确 list_products 是关键词/品类浏览，尚非语义推荐。
- 统一工具结果：模型可读的关键字段、UI/日志所需的结构化数据、稳定商品 ID。
- 需要上下文身份的请求由应用注入凭证，凭证不进入 prompt 或工具参数。
- shopping 技能从占位改成基于实际工具的流程。

验收：正常商品可查；不存在商品明确说明；断网/后端错误不说查询成功；价格和 SKU 与 API 一致；模型不能编造商品卡片。

从现有场景集中挑选固定只读冒烟用例，记录第一次基线。此阶段不开放写工具。

## 第二阶段：网页对话、会话与短期记忆

目标：登录用户可在网页流式对话，刷新后能恢复历史，并正确理解“刚才第二个商品”。

主要位置：src/server.ts、src/pi-session.mjs、.pi/extensions/harness/*；新增最小网页聊天入口，不改原仓库前端。

交付：

- Go 的 /agent/* 从 501 改成经鉴权转发到 Node；客户端维持同一业务 API 入口。
- 会话创建、发送消息、读取历史、取消 run，以及 SSE 文本、状态、商品卡片、错误和结束事件。
- 按账号校验会话归属，同一会话串行，client_message_id 去重；新建会话采用新的 pi SessionManager，不共用一个全局 Agent。
- MVP 先采用单实例、持久化挂载的 pi 会话文件；harness 保存会话/run 归属与状态映射。多实例恢复后续再设计。
- 存储最近推荐的有序 product_id / sku_id 列表，用于商品指代。近期对话复用 pi 上下文，长对话先复用原生压缩。
- 取消向模型和工具传播；记录已完成动作，不把取消当成业务回滚。
- 将网页可用的技能读取限制在受控资料范围，不能直接把当前本地开发入口的 read 文件权限开放给普通用户。
- 服务端使用独立运行凭证配置，不把个人 CLI 凭证作为生产服务配置。

验收：SSE 可显示；刷新可恢复；不同账号不可读彼此会话；重复发消息不重复执行；“第二个”对应最近相关推荐；切换话题不误引用；取消后停止后续工作；服务重启可以读取已持久化历史。

适配 10 条记忆场景，保留场景意图，但按新数据和工具结果断言，不要求旧 trace 字段或不稳定的具体推荐顺序。

## 第三阶段：自写 RAG

目标：商品选择有检索依据，知识回答有可追溯来源。

主要位置：src/retrieval/*、.pi/extensions/commerce/knowledge.ts、quality 下的新评测 runner。

入库链路：

```text
JSON / 原始知识文档
       -> 清洗 -> 按说明、FAQ、评价组织文档
       -> 切块 -> 索引 -> 查询
```

先建立词面检索基线与评测 runner，再根据漏召回情况加入 embedding、向量索引和重排。向量存储可以沿用原项目的 Milvus；在确认需要之前不增加服务依赖。

交付：

- 商品检索与知识检索分开：search_products 找候选，search_knowledge 找依据。
- chunk 保留完整正文，另外生成 snippet，避免像旧上传链路那样只对摘要建立索引。
- 保存 product_id、source_id、chunk_id、文档类型、版本与内容 hash；增量更新和删除有明确规则。
- 候选去重、品牌/品类/价格等可执行约束、无匹配结果处理。最新价格和库存通过 Go API 校验。
- 引用来源随工具结果返回；商品卡片只接受已校验的商品 ID。
- 先按需调用检索工具，不在每次请求前强制检索全部知识。

验收：300 条检索用例可跑；按商品/来源 ID 计算 Hit@K 和 MRR，分查询类型输出；FAQ 参考答案抽样评估依据正确性；无匹配不乱推荐。

评测目标在建立基线后确定，不能把计划阈值当成已实现效果。调参集与验收集按商品划分，避免同一商品的模板问题交叉调参。827 条 FAQ 中包含演示说明，需筛选后再用作答案质量评测。

## 第四阶段：加购与订单闭环

目标：用户明确要求后，真实完成加购和演示下单；重试不重复操作。

先实现 get_cart、add_cart_item、update_cart_item、delete_cart_item、list_orders、get_order，再开放结算、虚拟支付和收货。

主要位置：.pi/extensions/commerce/cart.ts、order.ts、harness/policy.ts，以及 Go 业务幂等接口和必要事务修复。

交付：

- 加购依据当前用户请求、明确商品及 SKU，不能由历史中的加购文本自动触发新动作。
- 下单前展示商品、数量、价格和当前选中范围，由用户确认该次操作；价格或选择变化后重新预览。
- 由应用生成稳定业务 action_id；Go 在业务事务中执行幂等去重并保存结果。pi 的 toolCallId 不作为跨重试业务幂等保证。
- 工具超时后先查询已执行结果，不盲目重试加购或下单。
- 卡片与成功文案来自实际业务返回。
- 接入交易前验证取消/超时库存补偿；优惠要么接通真实核销与金额计算，要么界面明确只做试算，不承诺未生效折扣。
- 支付保持虚拟支付，使用明确标签，不接真实资金或退款。

验收：加对商品和数量；错误 SKU、库存不足、越权订单被拒绝；重复确认只生成一次业务效果；断流后能查回订单；失败时不说成功；下单事务失败时库存和购物车保持一致。

阶段完成后形成第一个可交互 MVP：

```text
登录 -> 说需求 -> 检索推荐 -> 追问比较
     -> 指代商品 -> 加购 -> 确认结算 -> 虚拟订单
```

## 第五阶段：观测与持续评测

基础事件和测试从第一阶段开始记录，本阶段补齐展示和持续回归。

交付：

- run_id 关联模型、工具、RAG 来源、耗时、错误、token 用量和版本信息。
- 新管理页面查看真实调用链；不展示凭证，不以 UI 状态文案冒充实际执行记录。
- 每次变更执行只读冒烟、RAG、记忆、写操作幂等和端到端评测，比较上一基线。
- Prompt 和 skill 先由版本控制管理；出现明确的在线编辑需求后，再恢复后台发布系统。

原 131 条意图分类数据不强制要求新架构恢复旧 Planner；可把适用用例转成预期工具和任务结果检查。端到端数据中没有完整标准答案的场景，补充业务结果与依据断言，不能仅凭关键词计算总体准确率。

## 第六阶段：多模态与服务扩展

文本 MVP 稳定后再接图片上传/找相似商品、语音输入和 TTS。文件上传复用 Go + MinIO，图片检索另行建立评测和相似度基线。以后按实际并发需求增加多实例会话协调、任务队列和集中存储。

## 暂缓范围

先不引入多 Agent、长期用户画像、复杂工作流引擎、通用插件市场或新的向量中间件。pi 负责循环，插件提供工具和钩子，skill 描述工作流；交易授权、幂等和库存校验由代码保证。

## 下一轮建议范围

只实施第一阶段：只读客户端、3 个商品工具、shopping 技能和最小回归用例。验收通过再进入网页会话阶段，不一次性实现全部占位文件。
